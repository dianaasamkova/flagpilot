**How packages share code:** each package's `package.json` points straight at its TypeScript source (`"exports": "./src/index.ts"`), so there's no build step between packages. Next.js compiles them through `transpilePackages`. This is the simplest setup that works and is easy to explain.

## 4. Schema design (for your review; final rules come from CONVENTIONS.md)
Each error message says what's wrong, how to fix it, and gives an example. The model gets these messages back, so they must be actionable.

| Schema | Rules |
|---|---|
| `Environment` | `dev` · `staging` · `production` |
| `Region` | `EU` · `NA` · `APAC` |
| `FlagKey` | 3–64 characters, kebab-case (`checkout-new-button`): lowercase letters and digits, single hyphens, starts with a letter |
| `Targeting` | `regions`: at least 1, no duplicates. To reach nobody, turn the flag off instead of using an empty list |
| `EnvConfig` | `enabled` boolean · `targeting` · `rolloutPercent` whole number 0–100 · `revision` whole number ≥ 0 |
| `Flag` | `key` · `description` 1–280 characters · `owner` (team name, format set by the conventions) · `tags` up to 10, kebab-case, no duplicates · `envs`: one `EnvConfig` for **each** of the 3 environments |
| `FlagChange` (FP-7) | `flagKey` · `env` · `set` { `enabled`?, `regions`?, `rolloutPercent`? } · `reason` 3–200 characters, written to the history |

**`FlagChange` rules**, each with a passing and a failing test:
1. `set` has at least one field.
2. Setting `enabled: false` together with `rolloutPercent > 0` is contradictory, so it's rejected.
3. `regions` has no duplicates and at least 1 region.

A schema only sees the change itself. Rules that need the flag's current state, such as "a rollout above 0 needs the flag to be on", are checked by the server at propose time (FP-23).

**Tool inputs (FP-8):**

| Tool | Input |
|---|---|
| `list_flags` | `env`?, `enabled`?, `tag`?, `query`? (up to 50 characters) |
| `get_flag` | `key` |
| `propose_flag_change` | a `FlagChange` |
| `explain_flag_history` | `key`, `env`?, `limit` 1–50 (default 10) |

FP-8 also runs a **JSON Schema check**: a test converts each tool schema with `z.toJSONSchema()` and stores a snapshot. If a schema change alters what the model sees, the snapshot diff makes it visible in review. JSON Schema can't express refinements such as rule 2, so the server always validates again with zod (ADR-0003).

**Tests:** Vitest, in `packages/domain/test/`. For every schema:
- one valid example;
- one invalid example per rule;
- a check that the error message contains the fix hint;
- a type test (`expectTypeOf`) that the type from `z.infer` matches what we expect.

## 5. Settings worth knowing
- `tsconfig.base.json`: `strict`, `noUncheckedIndexedAccess` (array or record access may be `undefined`), `exactOptionalPropertyTypes`, `verbatimModuleSyntax`, `moduleResolution: "Bundler"`.
- `.npmrc`: `engine-strict=true`, so installing on the wrong Node version fails right away.
- CI runs on every PR and every push to `main`. It installs with `--frozen-lockfile`, so a lockfile that doesn't match `package.json` fails the build.

## 6. Risks we check first
| Risk | Check |
|---|---|
| TypeScript 7 isn't supported by typescript-eslint yet | Pin 6.0.3. CI fails if someone upgrades it by accident |
| Node 26 has no corepack | Install pnpm separately. CI uses pnpm/action-setup, which reads `packageManager` |
| zod 4 → JSON Schema may produce features Gemini doesn't accept | Snapshots in FP-8 now; the Gemini-specific check in M3 |
| `~/.local/node20` is on your PATH and may shadow Node 26 | After installing, `node -v` must print v26 in a new terminal |
